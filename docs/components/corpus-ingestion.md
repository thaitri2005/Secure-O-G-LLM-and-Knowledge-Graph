# Document ingestion (`graph_builder.corpus`)

**Direction (28 October 2026):** a GraphRAG application for drilling reports on open-weight models of about 7B or smaller ([specification](../PROJECT_DESIGN.md), [meeting](../requirements/supervisor-meeting-2026-10-28.md)). This guide records implemented behavior only. This pipeline is the current parser and chunker and the **baseline** for the VLM comparison (specification D-39, §5.10). Its row-safe Markdown table chunks carry over; OCR-engine tuning (VietOCR, RapidOCR, EasyOCR) is no longer planned work, and the engines remain for reproduction. Planned additions are VLM page parsing, multi-page table joining, parent/child chunk IDs and object storage (§5.11).

This guide describes the **implemented generic document pipeline**. It takes documents in many formats, reads every page in the most reliable way available (text layer, OCR of images, or full-page OCR), and produces passage and table chunks with page, region and section provenance. It is the pipeline for new and VPI documents. The older [PDF ingestion](pdf-ingestion.md) pipeline stays in place to reproduce the published GDR bundle and experiments E1–E4.

Measurements: [E5](../experiments/E5-ocr-engine-benchmark.md) (OCR engines), [E7](../experiments/E7-corpus-pipeline-smoke.md) (end-to-end smoke test), [E8](../experiments/E8-ak3-appendices-corpus-run.md) (AK-3 appendix portfolio: 44 PDFs, 463 pages, two workers).

## Setup

Use the README environment, then add the OCR stack:

```powershell
.\.venv\Scripts\python -m pip install -e ".[ocr]"
.\.venv\Scripts\python -m pip install --no-deps vietocr==0.3.13   # its metadata pins old packages; only the model code is used
.\.venv\Scripts\python -m graph_builder.corpus models            # once, online: PP-OCRv6 detector and VietOCR weights, digest-checked
```

The lock file installs the OCR packages and PyMuPDF. PyMuPDF provides original-PDF checks and source geometry for some K1 rules. The base Docling conversion can run without it. Without the lock, install `".[ocr,qa]"` to enable those checks and read the PyMuPDF licensing details in the dependency guide. [Dependencies](dependencies.md)

Models are stored in `data/interim/ocr_models/`. Conversion never downloads anything: the pipeline sets `HF_HUB_OFFLINE=1` and loads only local files (the VietOCR files are checked against pinned digests). Docling's layout and table models must have been fetched once, as for the PDF pipeline. [Model provenance](model-provenance.md) lists every model file with its source, revision, licence and SHA256, and says which ones the code pins and which are only recorded.

## Workflow

```powershell
python -m graph_builder.corpus init data/corpora/vpi                  # creates config.json, catalog.sqlite, store/, work/, exports/
# For the English workload, set ocr.engine to "rapidocr" in config.json before processing.
python -m graph_builder.corpus add data/corpora/vpi D:\docs --recursive --license-id vpi-internal
python -m graph_builder.corpus analyze data/corpora/vpi               # page plan only: how many pages need OCR
python -m graph_builder.corpus process data/corpora/vpi               # convert, chunk, check, validate
python -m graph_builder.corpus status data/corpora/vpi                # done / failed / pending, states (completed / failed / interrupted / not_started), rejected files
python -m graph_builder.corpus export data/corpora/vpi --name v1      # one bundle of everything done
python -m graph_builder.corpus k1 data/corpora/vpi --name k1 --models data/interim/ocr_models   # K1 chunk package of the PDFs done
```

- **`add`** registers files or folders, and also accepts `--url` for HTTPS hosts listed in `allowed_hosts`. Each file is checked from its bytes, not its extension. A copy is stored once under its SHA256 in `store/`, so identical files are registered once and reported as `duplicate`. Rejected files (legacy `.doc`/`.xls`, ZIP archives, encrypted PDFs, files over the limits) are recorded with a reason that says what to do.
- **`process`** handles each document independently and records the result in the catalog. A failure stays with its document and is retried with `--retry-failed`.
  - Re-running skips complete documents (manifest digests verified) and resumes partly converted ones from their cached segments.
  - `--workers N` runs N worker processes. Each loads its own models (about 2–3 GB of RAM), so use 1–2 on a 16 GB machine. A worker that dies (for example out of memory) stops the whole pool; see *Worker death and resume* below for what happens to the documents it held and to the ones that had not started.
- **`export`** stages a complete bundle, checks it against its `SHA256SUMS`, and only then publishes it as an immutable release, `exports/<name>/releases/<UTC time>-<digest>/`. `exports/<name>/CURRENT.json` names the current release and is switched with one atomic file replacement. An interruption at any step leaves the previous release current and complete, and the previous release is kept so a reader that resolved it can finish ([`publication.py`](../../src/graph_builder/publication.py)). Readers resolve the current release once with `graph_builder.publication.current_release(exports/<name>)`; an export written before this change (flat files in `exports/<name>/`) is still read until the next export of that name. Documents that failed or were never processed are listed under `held_back`. `--hold-review` also holds back documents with pages that need review.
- **`k1`** writes the PDF documents as a K1 chunk package in the same release layout as `export` (see [K1 chunk package](#k1-chunk-package)). It publishes only when every required document is ready; otherwise it exits with status 1 and publishes nothing (see [Completeness gate](#k1-completeness-gate)). `--only DOC_ID...` selects the required documents, `--k1-config` names the settings file, and `--legacy-chunks data/processed/gdr_chunks_full.jsonl` adds the old-to-new chunk id map. Use the same `--models` as for `process`, so that the processed documents are found.
- **`retire --only DOC_ID`** removes a document from future exports.
- **Run logs.** Every command also writes a timestamped log to `<corpus>/logs/`. `process` logs one line per finished document (pages, OCR pages, chunks, tables, review and missing pages, time), elapsed time, pages done and an ETA, plus a heartbeat every minute naming the documents still in progress.
- **AK-3 appendix example.** [`scripts/run_ak3_appendices.py`](../../scripts/run_ak3_appendices.py) downloads and verifies the AK-3 appendix portfolio, splits it into 44 PDFs, and runs `init`, `add`, `process`, `export` and `status` on `data/corpora/ak3_appendices`. Use `--workers 2` to run faster, and `--scanned-only` to process only the PDFs with scanned pages. Results: [E8](../experiments/E8-ak3-appendices-corpus-run.md).

## Supported inputs

| Format | How it is read | Chunk location |
|---|---|---|
| PDF | Per-page plan (below); Docling layout and TableFormer | Page, regions (PDF points, top-left origin), character spans |
| Images (PNG, JPEG, TIFF, BMP, WebP) | Full-page OCR | Page 1 (or frame), regions |
| DOCX, XLSX, HTML, Markdown, plain text | Docling structure, no OCR | `page: null`, section path |
| PPTX | Docling slides | Slide number |

Limits are set in the configuration: 200 MB and 3,000 pages per file by default.

## How each PDF page is read

`analyze` inspects every page with pdfium, without rendering, and assigns a mode ([`analysis.py`](../../src/graph_builder/corpus/analysis.py)):

| Mode | When | Conversion |
|---|---|---|
| `text` | The text layer is complete and well formed | Text layer only |
| `hybrid` | Good text layer, and images cover at least 15% of the page | Text layer, plus OCR of image regions it does not cover |
| `ocr` | Almost no text and a page-sized image (scan) or many vector paths (outlined text); or a garbled text layer | Full-page OCR, text layer ignored |

A text layer counts as garbled if any of these holds:
- replacement, private-use or control characters;
- many words with letters that neither basic Latin nor Vietnamese uses (typical of TCVN3/VNI legacy fonts: "ViÖt" for "Việt");
- many Vietnamese-marked words that are not well-formed syllables.

Invisible text left by a scanner's own OCR is kept when it passes these checks and replaced otherwise.

Pages are converted in segments: consecutive `text` and `hybrid` pages in batches of `segment_pages` (default 40), each `ocr` page on its own. Each segment is cached as gzipped Docling JSON, and the segments are joined with their original page numbers.

## OCR engine

The default engine is PP-OCRv6 text-line detection (ONNX) with VietOCR transformer recognition ([`vietocr_engine.py`](../../src/graph_builder/corpus/vietocr_engine.py)), registered as a Docling OCR plugin. It reads Vietnamese with all its marks as well as English. For English pages, `"ocr": {"engine": "rapidocr"}` measured better on the E5 English sample. Further OCR-engine tuning is not planned: VLM page parsing replaces it (specification D-39). The code default remains VietOCR until configuration is explicitly selected; `easyocr` remains for comparison. [E5](../experiments/E5-ocr-engine-benchmark.md) has the measurements. On a laptop CPU, expect roughly 25–50 s per scanned page; text pages take well under a second each after model loading.

## Quality flags

After conversion, the text attributed to each page is profiled with the Vietnamese syllable checker. A page read by OCR gets a status:

| Status | Meaning |
|---|---|
| `ok` | No problems found |
| `review` | More than 8% of its Vietnamese-marked words are malformed, or more than 5% of words use foreign letters |
| `missing` | It yielded fewer than 40 characters |

Chunks on flagged pages carry `"quality": "review"`. The flags are spelling heuristics, not accuracy measurements: a correctly spelled wrong word, such as a wrong tone that forms another real syllable, is not caught. Docling's per-page confidence scores are stored next to them.

## Outputs

Per document, in `work/<doc_id>/<fingerprint>/`:
- `document.json`: source identity, page analysis and quality, processing record;
- `chunks.jsonl`, `tables.jsonl`, `text.txt`;
- `docling.json.gz`: the full converted document;
- `segments/`: the conversion cache;
- `manifest.json`: output digests, written last.

The fingerprint hashes the configuration, the Docling versions and the OCR model digests. Changing any of them creates a new output directory instead of overwriting the old one.

By default it does not hash all of this package's own code: `PIPELINE_VERSION` is a constant that changes only when someone edits it, so a code change that alters the output reuses older results with the same settings. The optional top-level key `cache` (`{"code_version": true}`, absent from `configs/corpus/default.json`) adds a SHA256 over the processing source files (`graph_builder/corpus/` without `qa/`, `k1_*.py`, `export.py` and `__main__.py`, plus `graph_builder/ingestion/`; line endings normalised) to the fingerprint, so that any edit of those files creates a new output directory. With `cache` absent or `false`, fingerprints stay unchanged except for the explicit running-line semantics marker below; with it on, every first run after any edit of those files recomputes all documents (the safe direction). Dependencies outside these two packages and the OCR runtime are still not hashed.

The fingerprint still omits the complete layout and table model identity and the collected OCR runtime versions. In-process converter reuse includes format, mode, OCR settings, the local model directory, table mode and timeout. [Earlier cache review](../experiments/E9-repository-review.md)

Record schemas: [`corpus_document`](../../schemas/corpus_document.schema.json), [`corpus_chunk`](../../schemas/corpus_chunk.schema.json), [`corpus_table`](../../schemas/corpus_table.schema.json). Chunk offsets index `text.txt`, which is the chunks joined by two newlines. Every document is validated before its manifest is written: schemas, offsets, digests, regions inside the page, and table references.

## K1 chunk package

`k1` turns finished corpus output into the package that Track B reads (specification §5.11). It runs after `process` and changes nothing in the corpus chunk format, the fingerprint or the existing exports. Only PDFs are exported. Every required document must be a finished PDF, or nothing is published ([Completeness gate](#k1-completeness-gate)). This is a Track A proposal; Track C reviews the schemas. Results and measurements: [E30](../experiments/E30-k1-version-1-candidate.md).

| Module | Job |
|---|---|
| [`k1_build.py`](../../src/graph_builder/corpus/k1_build.py) | Builds the records of one document: ids, parents, forms, report context, page rebuild text |
| [`forms.py`](../../src/graph_builder/corpus/forms.py), [`text_layer.py`](../../src/graph_builder/corpus/text_layer.py) | Pairs form labels with values from the PDF text layer, using a template |
| [`report_context.py`](../../src/graph_builder/corpus/report_context.py) | Finds the report date and well of each daily-report page |
| [`table_recognition.py`](../../src/graph_builder/corpus/table_recognition.py), [`ops_tables.py`](../../src/graph_builder/corpus/ops_tables.py) | Recognise and rebuild the RIMBase "Operations Summary" table of a daily-report page from the PDF text layer (rule `table_rules.operations_summary`): recognition gates and reason registry, then rows, self-checks and merge |
| [`k1_export.py`](../../src/graph_builder/corpus/k1_export.py) | Writes and publishes the package, with `SHA256SUMS` |
| [`k1_validate.py`](../../src/graph_builder/corpus/k1_validate.py) | Checks schemas, references, offsets, checksums, page rebuild and context coverage before the release becomes current |
| [`legacy_ids.py`](../../src/graph_builder/corpus/legacy_ids.py) | Maps old chunk ids to K1 ids by text |
| [`k1_config.py`](../../src/graph_builder/corpus/k1_config.py) | Loads `configs/corpus/k1.json` |

### K1 completeness gate

`k1` publishes a release only if every required document is present and ready. The required documents are all active (not retired) documents of the corpus, or the ones named with `--only`. If one is missing or not ready, the export stops before it writes any package file. `exports/<name>/CURRENT.json` and the releases already published stay as they were, and the command writes a failure report instead.

**What changed.** Before the gate, `k1` skipped documents that failed, were not processed or were not PDFs, listed them under `held_back` in the manifest, and still published a release that became current. An unknown id in `--only` was refused with `Unknown documents: ...`. Now all of these block the export. A package that is published is complete for its scope, so `held_back` in its manifest is always `[]` (the key stays so that readers of old and new packages see the same manifest keys) and `held_back` in the result of `export_k1` is `0`. A successful export produces the same bytes as before the gate; this was compared with the pre-gate `k1_export.py` on synthetic corpora, and [`tests/test_corpus_k1_export_completeness.py`](../../tests/test_corpus_k1_export_completeness.py) covers the gate. To publish a subset on purpose, name it with `--only`. To drop a document for good, `retire` it.

**Why a document blocks (`reason`, with the `status` it is reported under).**

| `status` | `reason` | Meaning |
|---|---|---|
| `NOT_FOUND` | `unknown_required_document` | An id in `--only` is not in the catalog |
| `UNSUPPORTED` | `unsupported_format` | The document is not a PDF (`detail` holds the format) |
| `NOT_PROCESSED` | `processing_not_complete` | No finished job for the current fingerprint, or its outputs are missing or fail their digests |
| `FAILED` | `processing_not_complete` | The job recorded a failure (`detail` holds its message) |
| `FAILED` | `k1_build_failed` | Building the K1 records raised an error (`detail`: `<ErrorType>: <message>`) |
| `BLOCKED` | `report_boundaries` | The report-boundary check refused the document (`detail` holds its evidence) |
| `BLOCKED` | `document_not_ready` | The builder marked the document `BLOCKED`, `FAILED` or `UNSUPPORTED` |
| `BLOCKED` | `missing_or_duplicate_file`, `source_identity_mismatch` | The package record does not hold exactly one file with the catalog's id and SHA-256 |
| `BLOCKED` | `missing_or_duplicate_pages`, `missing_page_content` | Pages are missing, duplicated or without content |
| `BLOCKED` | `zero_chunks` | The document produced no chunk |
| `BLOCKED` | `foreign_file_records`, `foreign_document_records` | Records of another file or document ended up in this document's output |

**Exit codes.** `0` after a published release. `1` when the gate blocks, and for any other refused request (`ValueError`, `OSError`, `RuntimeError`, for example a missing `--name`, a staged package that fails validation, or a release name already used in the same UTC second). `130` after Ctrl-C. The command prints `FAIL: K1 release BLOCKED: required_documents_incomplete; failure report: <path>` through the command's log, which writes to standard output and to `<corpus>/logs/`; standard error stays empty. Calling `export_k1` from Python raises `K1CompletenessError` (a `ValueError`) with `.report` and `.report_path`.

**Failure report.** `exports/.k1-failures/<name>-<random>/failure.json`, one new folder per blocked attempt, outside every release and never named by `CURRENT.json`. It is UTF-8 with LF line endings and sorted keys, and it holds absolute source paths, so it is a local diagnostic: do not commit or share it.

```json
{
  "gate": "TC-07", "status": "BLOCKED", "reason": "required_documents_incomplete",
  "export_name": "<name>", "corpus_fingerprint": "<fingerprint>",
  "required_documents": [{"doc_id": "...", "sha256": "...", "pages": 2}],
  "ready_documents": [{"doc_id": "...", "file_id": "...", "sha256": "...", "document_type": "...", "pages": 2, "chunks": 3, "tables": 1, "forms": 0}],
  "blocked_documents": [{"doc_id": "...", "sha256": "...", "source": "...", "original_name": "...", "status": "NOT_PROCESSED",
                         "reason": "processing_not_complete", "detail": "not processed", "pages_held": 2,
                         "corpus_chunks_held": null, "k1_chunks_held": null,
                         "source_references": null, "source_reference_error": null}],
  "missing_document_ids": ["..."], "unexpected_document_ids": [],
  "counts": {"required_documents": 2, "ready_documents": 1, "blocked_documents": 1, "published_documents": 0,
             "pages_held_known": 2, "pages_held_unknown_documents": 0,
             "corpus_chunks_held_known": 0, "corpus_chunks_held_unknown_documents": 1,
             "k1_chunks_held_known": 0, "k1_chunks_held_unknown_documents": 1},
  "published": false, "current_updated": false

```

A count that could not be determined is `null` (and counted under `..._unknown_documents`), never `0`. `source_references` lists the `chunk_id`, `pages`, `source_spans` and `regions` of the corpus chunks the blocked document holds, when its `chunks.jsonl` can be read; otherwise `source_reference_error` says why.

**Limits.** The gate checks presence and structure, not the accuracy of the extracted text against the PDF. A corpus with no active document exports an empty package, as it did before. Releases are named by the UTC second and the content digest, so exporting identical content under the same name twice within one second is refused. Consumers read a package through `CURRENT.json` or a release folder and never list `exports/`; nothing in the repository reads `held_back` from the manifest (inspected: `platform/load_k1.py` stores the manifest as it is and uses only `counts`; `graphrag/data.py` reads `CURRENT.json`).

**Files in a package.** `files.jsonl`, `pages.jsonl`, `tables.jsonl`, `forms.jsonl`, `parents.jsonl` and `chunks.jsonl` (one JSON record per line), `text/<file_id>.txt` (the text that chunk offsets index), `manifest.json`, `SHA256SUMS`, and `legacy_chunk_ids.json` when `--legacy-chunks` is given. The package has no timestamps or absolute paths, so the same inputs give byte-identical `SHA256SUMS`.

**Ids.**

| Id | Form | Example |
|---|---|---|
| File | `f` + first 16 hex digits of the PDF SHA256 | `f673c77409ffeafb7` |
| Page, table, section parent, form parent | `<file_id>:p<n>`, `:t<n>`, `:s<n>`, `:f<n>` | `f673c77409ffeafb7:t3` |
| Chunk | `<parent id>:c<n>` | `f673c77409ffeafb7:s5:c0` |

K1 ids contain no `#`. Tables are one logical table per corpus table (`parts` has one element); joining tables across pages is the option `table_join` (see below); a joined table is one record with several `parts`. Table chunks keep the `row_start` and `row_end` the corpus wrote.

**`doc_id` policy.** The end-of-well report keeps its registry id (`add --doc-id gdr882_ak3_eowr`). The daily-report attachments keep the catalog default, a slug of the file name plus 8 hex digits of the SHA256. These ids are hyphenated and keep `dailyreport` and `-appx-NN-`, which Track B uses to find the daily reports and their appendix number.

**Which profile is the default.** After the option measurements of 25 November ([E62](../experiments/E62-track-a-option-measurements.md), Track A log A-D07), `configs/corpus/k1.json` keeps grid recovery, the Operations Summary and ruled-panel rules, `table_join` as shipped and `section_context` on, and has the other settings that main turned on on 24 November off. The paragraphs below that say "default" or "standard" K1 profile describe the profile of 24 November, kept as `configs/corpus/candidates/k1_standard_24nov.json`; pass it with `--k1-config` to use it.

**Rule selection.** The default K1 profile uses `evidence_routing`. Each enabled table reader checks the page for its own title, headings, and structure. The report type comes from a recognized PDF header and defaults to `other` when the evidence is absent or conflicting. An unclassified document can still receive a table repair. Set `evidence_routing` to `false` in a copy of the profile to replay the previous filename-based selection.

**Forms.** The RIMBase reader requires the labels in `configs/corpus/rimbase_form_template.json` and the printed `Operations Summary` title. Other default readers verify the coordinates of the daily header and recover supported fields from its typed values. Generic colon pairing is off (`forms.generic` in `configs/corpus/k1.json`). Each form is a parent of type `form` with one chunk of `Key: value` lines.

**Report context.** Chunks of daily reports (`report_context.document_types` in `configs/corpus/k1.json`) carry `context.report_date` and `context.well`. The verified template form supplies them first. Pages without a form use the regular expressions in `report_context.date_patterns` and `well_patterns` on the PDF text layer. When both exist and disagree, the form wins and the manifest lists the page under `form_conflicts`. A passage that crosses a change of report date is split. A daily-report page with no context must be listed under `pages_without_context`, or validation fails.

**Operations Summary tables.** Docling can merge the `Operations Description` and `Non-Prod` headers, move the `X` marker, spill words into other cells or miss the table. When `table_rules.operations_summary` is enabled, [`table_recognition.py`](../../src/graph_builder/corpus/table_recognition.py) checks evidence from the PDF text layer. [`ops_tables.py`](../../src/graph_builder/corpus/ops_tables.py) reads the rows of a recognized table, verifies them and merges the result into K1 chunks and tables. The profile defines the title words, column labels, value patterns and tolerances in the `schema`, `recognition` and `tolerances` blocks. The reader measures distances as fractions of the page width or of the title or header text height.

*Supported format* (checked by four gates, each with a different kind of evidence):

| Gate | Evidence | Requirement |
|---|---|---|
| G0 | precondition | the page is upright (rotation 0) |
| G1 | words | the title words sit next to each other on a line; every other word of that line is an annotation in a column of its own (far from the title in `em_title`), not a sentence glued to it |
| G2 | geometry and structure | the line right under the title holds all column labels of the schema, once each, in order and left to right (other splits of the same words are accepted) |
| G3 | meaning | the next line starts with two time tokens |

A line with only one of the title words (the header `... Operations Description ...`, a `Management Summary` title) is not a mention of the table. Annotations on the title line, such as `1 record not printed`, are accepted on either side, in any font, and recorded in the sidecar. After the gates the rows are read (two times, hours, depth, an optional code, a description that may wrap, a mark column that holds only the exact mark glyph), and the page is rebuilt only if every self-check passes: valid times, row count, Elapsed against From and To, at most one mark per row, the words and glyphs of the table band equal the rebuilt cells, no stray time line after the table, and no line that is neither a row, a following title nor a centred section title directly under the table. The table then replaces Docling's table under the same `table_id`, or, when Docling found none, is added with the next free number of its file. It has one header row and one column per schema label, its `source_ref` starts with `textlayer:operations_summary:`, and its chunks are split like any table chunk.

The `Code` column accepts alphabetic codes and hyphenated numeric codes such as `3-2-1`. Both formats must pass the printed column geometry, elapsed-time and source text checks. Cell QA independently verifies the rebuilt column locations against the PDF. [E49](../experiments/E49-track-a-compound-tables.md)

*Not supported* (the Docling table is kept and the reason is recorded; nothing is guessed): rotated pages and pages without a text layer; a header with extra, missing, repeated or reordered labels, or one that is not directly under the title; a title inside a sentence or a contents line; words near the title that are neither the same phrase nor a column of their own; a line between the title and the header; a standalone number in the `Code` column or a code outside its configured grammar; marks printed as anything but the exact glyph; tables over several pages and continuation pages without a title; a following section title that is not centred; other report families and other page sizes or fonts than the ones evaluated (`NOT EVALUATED`). An annotation that sits on a line of its own away from the title or the table is not detected.

*Four states.* Every occurrence of the title (and every page that mentions the title or holds a Docling table with an Operations header) leaves one sidecar record with one of these states and a machine-readable `reason`:

| State | Meaning | Reasons |
|---|---|---|
| `SUPPORTED_AND_VALIDATED` | gates and self-checks passed and the table was merged. "Validated" means consistent with the text layer of that page, not compared with the page image | none |
| `UNSUPPORTED_FORMAT` | a recognition gate or the precondition failed; Docling is untouched | `no_title`, `no_header`, `header_not_adjacent`, `header_labels_missing`, `header_extra_labels`, `header_order_mismatch`, `no_rows`, `rotated_page` |
| `RECOGNISED_BUT_FAILED` | the gates passed but reading, a self-check or the merge failed; Docling is kept | `time_invalid`, `column_mismatch`, `trailing_line` (also used for a stray line below the table and for a lone line stuck to it), `row_count_mismatch`, `elapsed_mismatch`, `x_unmapped`, `word_mismatch`, `docling_extent_mismatch`, `ambiguous_docling_match` (also when a Docling table only partly overlaps the rebuilt one), `docling_multipage` |
| `PARSING_FAILURE` | an unexpected exception on one page or table, recorded with the class name; the other pages and tables are still processed, `MemoryError` is not caught | `text_layer_read_error`, `rule_exception`, `merge_exception` |

A fallback result is never presented as validated, and no confidence number is computed. `no_title` details name the first rejected mention: `not_found`, `multiple_title_phrases`, `embedded_in_text`, `ambiguous_gap` or `annotation_too_long`.

*Reading the sidecar.* `export_k1` returns the records as `table_repairs`, outside the package (the K1 manifest and schemas are unchanged; moving the reasons into the contract is task A-104). `scripts/export_k1_ops_rebuild.py` writes them to `table_repairs.NAME.json` and a per-family summary to `table_repairs.NAME.summary.json`. A record has `doc_id`, `page`, `index` (the nth accepted title of the page, so a rebuilt table keeps its `source_ref`), `document_type`, `rule`, `state`, `stage` (`precondition`, `recognition`, `read`, `validate`, `merge` or `runtime`), `status` (`rebuilt` or `fallback`, for older readers), `reason`, `detail`, `action` (`replaced`, `added` or `kept_docling`), `table_id`, and:

| Field | Meaning |
|---|---|
| `evidence` | what each gate measured and the margin to each threshold in `em` (reading aid only, never part of a decision); `decision` and `rejected_at` (`G0` to `G3`) |
| `annotations` | words on the title line (`side` left or right, `kind`, `count`; `unclassified` when no configured kind matches) and, as a hint only, a line right above the title (`side: above`, `owner: uncertain`: it may belong to the table above) |
| `completeness` | `partial_in_source` when an annotation says records were not printed (the rebuilt table holds only the printed rows, and the K1 chunks do not carry the annotation: consumers of K1 cannot see it, the decision is deferred to A-104); `unclassified_annotation` for an unknown annotation; `null` otherwise, which is not proof that nothing is missing |
| `rejected_mentions` | lines that name the table but are not its title (sentences, contents lines) |

The summary file counts records per family (`document_type` and `rule`), per state and per state and reason, with `parsing_failure_rate` and `annotations_above`; the script prints a warning (without stopping) when `parsing_failure_rate` of a family is above `--warn-parsing-failure-rate`. These are counts, not a measure of scalability.

*Conventions and limits.* A description that the report truncates with `...` (printed in the x range of the `Non-Prod` column) keeps the dots at the end of the description cell; the mark cell holds only the mark. A description word that is exactly the mark glyph and sits under the mark header cannot be told from the mark by geometry; it is read as the mark unless the row has two such tokens (then `x_unmapped`). Text chunks are never edited, so the words of a rebuilt table also remain in the loose text chunks of the page, which can duplicate hits for a consumer that reads both. A `trailing_line` reason hides three situations (a wrapped line with another indent, a footer and a following title that is not centred); read `detail`. To label a new annotation, add an entry to `annotation_kinds` (a `kind`, a pattern with one numeric group, and a sample the pattern must match); an annotation never needs a kind to be accepted. [`scripts/evaluate_ops_tables.py`](../../scripts/evaluate_ops_tables.py) measures the result against the PDFs (known documents and a document-level scan), [`scripts/regress_ops_tables.py`](../../scripts/regress_ops_tables.py) compares a release with a baseline (ids, non-operations tables and chunks, Track B events), and [`scripts/export_k1_ops_rebuild.py`](../../scripts/export_k1_ops_rebuild.py) writes an export together with the sidecar.

**Merged table cells.** Docling repeats the text of a cell that spans several rows or columns in every grid position it covers, and so does the table Markdown of a chunk. `chunking.table_markdown` (optional; `docling` or absent keeps the old output, `span_once` writes the text once at the top-left position and leaves the covered positions empty) changes only the Markdown of tables that have merged cells. A header cell that spans columns of a stacked header (more than one header row) keeps its text in each column, because the flattened label `Group - Sub` is the column's meaning. Table records (`tables.jsonl` cells, grid, spans), row counts, row ranges and K1 ids do not change; a table whose chunk text gets shorter can need fewer chunks, so a continuation chunk id (`...:cN`) can disappear. The option is part of the fingerprint, so `process` writes a new output directory; the default configuration does not set it. The QA cross-representation check accepts an empty chunk cell at a covered position when the record repeats the origin text there. `span_once_keyed` (A-431) renders like `span_once` but (1) keeps the text of a row-spanning key cell (a body cell in the first column, or flagged as row header) on every row it covers, so each row line keeps its key, and (2) cuts the table chunks at the row boundaries of the `docling` rendering, so chunk ids (`...:cN`) and `row_start`/`row_end` stay identical to the default output while the text gets shorter. The decision uses only span structure and position, never text equality; a row-spanning cell outside the key columns is written once.

**Section context (A-434).** Docling labels any prominent line a section header, so on reports with a running page header the banner of every page (`Daily Drilling Report Well ID: AK-3`), a report-date stamp (`Report For 12-Aug-16`) or an e-mail address becomes the `section` of the passages under it. The optional K1 configuration key `section_context` (on in `configs/corpus/k1.json` since 25 November 2026, E62 and A-D07; the block is also kept on its own in [`configs/corpus/section_context.json`](../../configs/corpus/section_context.json)) removes such headings from `section` and `section_path` of chunks and section parents (the value becomes `null` or the path gets shorter; no section is assigned in its place). A heading is dropped when (1) it matches a configured `value_patterns` entry (`report_date`, `email`) or (2) it is built from banner lines: lines in the header or footer band (`furniture`: fractions of the page height) that repeat on at least `min_pages` pages and `min_page_share` of the readable pages, compared with numbers masked and with each banner line taken from its beginning, so a sub-heading that is only a slice of a banner line is kept. Pages with a rotated display and documents shorter than `min_pages` give no banner evidence. The optional `numbered_hierarchy` list (`scheme` and a pattern with one group that captures the dotted number) gives a numbered heading the earlier headings of the same document that carry a shorter number prefix (`VI.` then `VI.1`) as ancestors in `section_path`; ancestors that were never seen are not invented, and Docling reports every heading at the same level, so the path is flat without it. Both parts change only `section` and `section_path` values: the section numbering behind the ids (`<file_id>:s<n>`) still follows Docling's original paths, so chunk and parent ids, text, offsets and every other field stay identical. The key enters `manifest.json` (`config.k1`) and so the package identity; the export result lists the dropped headings per document (`section_context`), outside the package. A text layer that cannot be read leaves every section unchanged and is reported in that list.

**Form recognition (optional, development candidate).** The optional K1 configuration key `form_recognition` (default absent; it is not in `k1.json` or `default.json`; pass a candidate with `--k1-config`) adds `Key: value` fields that [`form_recognition.py`](../../src/graph_builder/corpus/form_recognition.py) finds on the PDF text layer. A registry of explicit label spellings decides what is a label; there is no fuzzy or case-insensitive matching, and a region with an ambiguous or unproven label, value or table neighbour adds nothing. It cannot be combined with `form_blocks`. Two kinds of additions exist, and the decision list of the builder marks each accepted field with its `attribution`:

| Attribution | Where | Condition |
|---|---|---|
| `P1` | the header part of a page that the template extractor read as a RIMBase form (above the template's `header_boundary`) | no further test; fields that overlap existing fields are skipped; existing fields and `form_id` stay as they are |
| `P2` | any other region of a page, including a page with no template form | the region needs at least `eligibility.min_labels` distinct labels, `min_rows` rows and `min_nonempty` filled values, with aligned keys and values. On a page without a template form it creates a new form (`method: generic`, `verified: false`, chunk quality `review`), numbered after all other forms so that no existing form id changes |

[`k1_form_recognition_v1.json`](../../configs/corpus/candidates/k1_form_recognition_v1.json) enables both. The optional boolean `non_header_regions` inside `form_recognition` selects between them. Absent or `true` keeps the behaviour above, so the configuration files that existed before the option give the same output as before. `false` turns the whole `P2` path off: no field and no form outside the template header, and no region eligibility evaluation or `insufficient_region_evidence` finding. Findings that are not about region evidence (for example `no_label_value_separation`) are still recorded. Header fields (`P1`) are the same as in the combined mode. Any other value than `true` or `false` is refused when the configuration is loaded. [`k1_form_recognition_header_only.json`](../../configs/corpus/candidates/k1_form_recognition_header_only.json) is the same registry and settings with `"non_header_regions": false`.

*Status.* `P1` may be enabled on its own in development with the header-only candidate. `P2` is deferred: it stays disabled and is not accepted for any shared configuration, and the combined candidate is not recommended. An earlier internal evaluation run of form recognition on a daily-report document ended with a failed safety check whose cause is not resolved; its results were discarded and nothing here depends on them. The tests use synthetic text layers only; results on development documents are not general accuracy, and no independent evaluation exists (`NOT EVALUATED`). The registry was written for one daily-report family and has not been tried on other report families.

*Known effects when the key is present* (schema and K1 contract unchanged):
- A form chunk that receives added fields keeps its `chunk_id` but its text and `sha256` change. `char_start` and `char_end` of the chunks after it in the same document move, and `text/<file_id>.txt` and the page rebuild digest (`filtered_text_sha256` in `pages.jsonl`) of an affected page change. A consumer that compares chunks by hash or caches by text sees these chunks as changed.
- The package identity changes, because the key is part of the K1 configuration that enters it. Changing `non_header_regions` changes it again; removing the key gives the identity of the same configuration without it. The corpus fingerprint does not change, so processed corpus output is reused.
- The builder returns the decision list (accepted fields with their `attribution`, and the reasons for fields that were not accepted), but `k1_export.py` does not write it into the package and no schema field carries it. A reader of the package cannot tell an added field from a template field, except that an added field has `verified: false`.
- `verified` of the form stays `true` and the form chunk keeps quality `ok` when a `P1` field is added to a template form, although that field has `verified: false`. Only a form made from `P2` fields is `verified: false` with quality `review`.
- Only the K1 schemas and offset/checksum rules were checked on synthetic records with added fields. No Track B or Track C consumer has been run on a package that contains them (`NOT EVALUATED`).

**Footer lines.** The corpus filter removes lines that repeat on many pages, which also removed the weather line `Vis.: 6 Temp: 58 ...` of the daily reports. `filters.keep_line_patterns` (optional list of regular expressions; absent means the old behavior) protects matching lines. [`configs/corpus/daily_reports.json`](../../configs/corpus/daily_reports.json) sets it for the weather labels. It is a corpus setting, so `process` must run with it; `k1` only reads the result.
**Numbers lost as running lines (optional; table-cell semantics v2).** The line frequency key replaces every digit run by `#`, so a numeric table cell can share the key of a page counter. With `filters.running_line_position_tolerance` set (fraction of page height, above 0 and at most 0.5), ONLY table-cell occurrences are judged by positional repetition: their key must also repeat at the same vertical position on enough distinct pages. Text items keep the legacy removal decision. The cell guard runs after block selection; a rescued cell cannot rescue nearby text, and mixed logical lines never rescue text items. The key absent preserves legacy output. Real table data repeated at the same position can still be removed; position alone cannot distinguish it from furniture. Chart labels (DR-10) are not covered.

The processing fingerprint includes `running_line_semantics: 2` only when the tolerance key is present, even when `cache.code_version` is absent/false. Old global-tolerance work directories therefore cannot be selected for the new semantics; they are retained, and the new directory is processed from conversion cache when available. With the tolerance key absent, this marker is absent and frozen/OFF fingerprints remain unchanged. `cache.code_version` remains independently opt-in.

On the DEV/SEEN documents the selected semantics restores five source-backed table-cell occurrences (`0` twice, `150`, `536`, `3600`) in 78-32 pages 86/93, keeps the chart artefact `3` on page 87 removed, and restores zero text lines in akutan_3. All 1,122 furniture removals remain. Earlier 154 chart-label / 155 total-line restoration counts and akutan_3 ID drift describe the previous global semantics, not this option now. **Running lines in short daily reports.** [`configs/corpus/daily_reports.json`](../../configs/corpus/daily_reports.json) sets `filters.running_line_min_pages` to 3. With the usual frequency of 0.5, one occurrence would otherwise satisfy the share threshold in a one- or two-page report. The daily-report profile requires a line to occur on at least three distinct pages as well as meeting the configured frequency. This guard preserves margin data on one- and two-page reports. A print stamp or page counter can also remain in the chunks. The filter still removes qualifying headers and footers in longer reports and protects lines matching the weather patterns. Use the profile with `corpus init --config configs/corpus/daily_reports.json`. For an existing daily-report corpus, set the same key in its `config.json`, rerun `process` and export a new K1 release. **Truncated text read as a TOC line (C-03c, optional).** A text item whose last characters are three or more dots (`...`, with or without a following number) is excluded as a table-of-contents dotted-leader line (`dotted_leader_toc`; `TOC_LEADER` in [`filters.py`](../../src/graph_builder/ingestion/filters.py)). Report software that cuts a long cell and draws `...` therefore loses the whole sentence in front of it (in the 50 evaluated PDFs: 62 items in two daily-report families, for example a `Comments:` cell of 68-32 page 28). The optional setting `filters.toc_leader_min_dots` (integer 4 to 100; absent means the old behavior; it enters the processing fingerprint) lets a run of fewer dots count as a leader only when a page number follows it, or when the item has no letter or digit at all (a bare `...`, still excluded). Long leaders (`...... 12`) stay excluded. It is not set in `configs/corpus/default.json` or `k1.json`. With it set, the chunk text, `char_start/char_end`, `sha256` and `source_spans` of the chunks that receive the kept text change, and chunk ids can shift if a longer chunk no longer fits `max_chars` (in the 50 evaluated PDFs no id was added or removed); reload the affected documents. A table of contents whose leader has fewer dots than the setting and no page number in the same item is read as data.

**Sideways pages (C-03, optional).** A page whose text is not upright when displayed (for example upright text with `/Rotate 270`, or text drawn sideways with no `/Rotate`) changes the table and reading structure that Docling returns, with no warning: on 9 synthetic copies of three one-page tables the table dimensions differed from the upright original in 9 of 9 sideways copies and in 0 of 9 copies whose `/Rotate` only compensates for turned content (so `/Rotate` alone is not the cause). The optional setting `analysis.page_orientation` (`{"mode": "flag" | "normalize"}`, plus `min_chars`, `dominant_share`, `angle_tolerance`, `max_steps`) measures the glyph baseline direction of each page with PDFium ([`orientation.py`](../../src/graph_builder/corpus/orientation.py)) and stores an `orientation` record per page in `document.json` (`state` upright, sideways, mixed, no_text, no_text_rotated or failed; `status` SUPPORTED, UNSUPPORTED_FORMAT or PARSING_FAILURE; `reason` `rotated_page`). `flag` changes nothing else. `normalize` also converts a working copy `input-upright.pdf` in which `/Rotate` of the sideways pages is set so the text is upright (the stored PDF is never modified); K1 page size and `regions` of those pages use the conversion frame. `pages.jsonl` records `source_rotation` and `working_rotation` in `rotation_attempts`. The cell-evidence sidecar uses the displayed original PDF frame. Scanned or OCR pages with `/Rotate` and mixed-direction pages are reported (`no_text_rotated`, `mixed`) and not corrected. The optional QA check `qa --orientation` turns the records into `ROTATED_PAGE_*` signals. The key is absent from `configs/corpus/default.json`; setting it changes the corpus fingerprint.

Use `analysis.page_orientation.mode` set to `verify` to compare both conversions on text-layer segments that contain a sideways page. The verifier keeps the original orientation if the comparison is unavailable, source word coverage falls, a source numeric occurrence disappears or the table count falls. When existing numeric rows change, each original table needs a distinct match with stronger evidence from the printed PDF cell locations. Mixed decisions within one segment trigger a conversion with only the accepted corrections. QA reports the decision and counts for each tested page. [E48](../experiments/E48-track-a-verified-continuations.md) · [E52](../experiments/E52-track-a-source-panels-and-cold-processing.md)

**Worker death and resume (C-04).** Each document has four states, derived from the files and the catalog (the `jobs` table still only holds `done` and `failed`): `completed` (manifest and every output digest intact), `failed` (the catalog holds a failure), `interrupted` (a worker started the document, left `job.running.json` in its work folder and never reported: killed, or the run was stopped), `not_started` (nothing usable and no marker). A worker removes its marker when the document finishes or raises an ordinary exception. When a pool worker dies, Python stops every worker; `process` then records the documents whose results had already arrived, queues the documents that had not begun in a new pool, and re-runs each document that was running one at a time. A document that kills a worker while it runs alone is recorded as `failed` (`worker process died while this document ran alone`); the others (killed only because the pool broke) finish normally. A pool that dies before any document started is not retried: the documents stay `not_started` (counted as `not_started` in the result, exit code 1) and are simply pending for the next run. A later `process` run skips `completed` documents, re-runs `interrupted` and `not_started` ones without `--retry-failed`, retries `failed` ones only with `--retry-failed`, and records a finished output whose catalog row was lost with the process instead of recomputing it. `status` adds a `states` count and lists interrupted documents; it only checks that the manifest exists (cheap), `process` verifies the digests. A marker alone cannot tell a crashed run from one that is still running, so `status` during a live run lists the documents in progress as `interrupted`. If the whole process is killed in single-worker mode the document is left `interrupted` and nothing re-runs it automatically.

**Working copy of the source (REL-F1).** `process` works on a copy `input.<ext>` of the stored source in the document's work folder (a hard link, or a copy when hard links are unavailable) and removes it when the document finishes. A copy left by a failed or killed run is reused only if its SHA256 equals the catalogued one; otherwise it is rebuilt from the store through `input.<ext>.partial` and published with `os.replace`, so `--retry-failed` works after the store has been repaired without deleting anything by hand. If the stored blob itself does not match, the document fails with `SourceChecksumError: source_checksum_mismatch_store: <blob path>, <actual sha256>, <expected sha256>` (stored in the job error and shown by `status`), no wrong file is left in the work folder and the blob is not modified. `source_work_copy_replace_failed` reports that the stale copy could not be replaced (for example because another program has it open). A blob that is missing from the store still raises the operating-system error. Running two `process` commands on the same corpus at once remains unsupported.

**Quarantine of uncertain text (optional).** The optional `chunking.quarantine` object (absent from `configs/corpus/default.json`; absent means the output is byte for byte the old one; it enters the processing fingerprint) never rewrites, drops or reorders text. It records machine-readable findings in `statistics.quarantine` of each document and, when `scripts/export_k1_ops_rebuild.py` exports a package, in the sidecar `quarantine.<name>.json` outside the package, with a join `chunk_id -> [{reason, class, source}]` over the text chunks. Switches (all `false` by default): `list_dropped_items` (every dotted-leader / index item the filters leave out, with page, text and `leader_dots`, and the text removed from items by the running-line filter, instead of only the count in `statistics.dropped`), `list_page_status` (per page `grid_supported`, `few_label_cells`, `ocr_page`, `rotated_page`, `page_size_mismatch`, `page_error`, `no_text_items`), `scan_visibility` (reason `text_not_visible`: words in the text layer but clipped away at the item's box and visible nowhere on the page; informational reasons `text_not_in_layer`, `text_displaced` and `text_tail_clipped`, which are recorded but do not mark chunks unless `review_reasons` lists them), `scan_value_before_label` (an item that starts with the value of the label to its left and ends with the next cell's label, found from a column gap in the word boxes) and `mark_review` (chunks that hold a `text_not_visible` or `value_before_label` finding get the existing K1 v1 value `quality = "review"`; `review_reasons` narrows the list). `quality = "review"` and the sidecar are warnings, not isolation: Track B ignores `quality` and Track C only stores it. Source: [`quarantine.py`](../../src/graph_builder/corpus/quarantine.py).

**Table cells against the PDF (optional).** `chunking.quarantine.scan_tables` (default false; absent or false = byte for byte the old output, and the quarantine report does not echo the table keys) compares the cells of every table of a paginated PDF document with the words of the PDF text layer in the table's box (no Docling, no model). A token that is unique among the cells and among those words has a known place on the page; two tests use only those places. `table_cell_spans_blocks`: the words of one cell, in the order of the cell text, jump back up a line, back left on the same line, or across a wide gap between neighbours (the cell joins labels and values of separate blocks, header words of several columns, or two tables). `table_geometry_inconsistent`: at least `table_max_geometry_ratio` (0.4) of at least `table_min_testable` (8) testable cells overlap no other cell of their own column or row (the grid does not follow the page, e.g. a sideways page). Findings carry `table_id`, `source_ref`, the table box and the cells; with `mark_review` the chunks of that table get `quality` `review` (a warning that a consumer may ignore, not isolation; no text is changed, dropped or moved) and the sidecar joins them through the K1 table id (a table rebuilt later by `table_rules` is not joined). Tables that cannot be judged are counted with a reason in `statistics.quarantine.tables.not_examined` (`ocr_page` also covers hybrid pages, `rotated_page` is any /Rotate other than 0 and 270, `page_size_mismatch`, `little_text_layer_in_region`, `no_region`). Page rotation 270 is read in the upright frame. Evidence: DEV/SEEN only (50 PDFs); independent evaluation NOT EVALUATED. Candidate: `configs/corpus/candidates/rimbase_table_quarantine_candidate.json`.

**Tables cut by a page break (FR-25).** The default profile checks the last body table on one page against the first body table on the next. It requires an explicit printed continuation with compatible headers or a regular depth or index sequence within the same verified report. Geometry, report identity and numeric restarts can block a join. The earlier repeated-header comparison is available in `configs/corpus/candidates/k1_table_join_candidate.json`. [AWS guidance on multi-page tables](https://aws.amazon.com/blogs/machine-learning/postprocessing-with-amazon-textract-multi-page-table-handling/)

`table_join.continuity.merge_split_rows` also recovers a narrative cell cut across two pages. It requires a printed continuation, aligned borders and headers, and a distinct text column supported by numeric anchors in neighboring records. QA can trace the resulting row to the individual fragments on both source pages. An independent record or a complete preceding sentence keeps its original row.

A joined table keeps the first table's ID and one grid. `parts[].page` and the row ranges identify where each retained row came from. `parts[].header` keeps the repeated header removed from the logical grid. Chunk text and its offsets are preserved, while continuation chunks use the joined table ID and row numbering. The export returns per-pair reasons and absorbed IDs. The candidate covers native text tables. OCR and rebuilt tables need their own join evidence. **Old-to-new chunk ids.** `--legacy-chunks` maps the 60 chunks of `gdr882_ak3_eowr` in the main bundle to K1 chunk ids. Chunks match first on exact text with whitespace collapsed, then on token Jaccard similarity of at least 0.9; each new chunk is used once, and the rest are `unmapped`. `legacy_chunk_ids.json` holds one record per old chunk (`old_chunk_id`, `new_chunk_id`, `method`, `jaccard`, `old_page`, `new_page`) and is covered by `SHA256SUMS`. It is a migration aid, not a drop-in: a chunk the new parser split or merged stays unmapped.

## List markers

Set `chunking.preserve_list_markers` to `true` in the corpus configuration to retain markers such as `16.3` and `7.` in chunk text. The pipeline restores a marker only when Docling has a structured list item and its original text contains exactly that marker followed by the current item body. Items with multiple provenance spans keep their converted text.

The option is off by default. Enabling it changes the processing fingerprint and can change chunk boundaries. Run `process` again, export a new K1 release, and compare it with the baseline using `qa --fidelity` on text PDFs.

## Limitations

- This is a local processing tool, not an authenticated application boundary. Parsing isolation, enforced network denial and expanded-archive/image resource limits remain required before shared/private-data use.
- Remote URL redirects are checked after `urlopen` follows them; the allow-list is not a complete SSRF defense. Keep acquisition operator-controlled.
- `retire` excludes future exports; it does not revoke older exports or answers. Immediate application withdrawal and restore tombstones remain planned.
- Standalone wheel/schema packaging and a reproducible Linux/GPU environment have not been verified. Run from the documented Windows checkout environment.

- Handwriting, stamps, heavy skew and multi-column reading order on scans are not evaluated; [E5](../experiments/E5-ocr-engine-benchmark.md) used rendered pages.
- VietOCR lacks some symbols ("°").
- Two workers on a 463-page corpus work ([E8](../experiments/E8-ak3-appendices-corpus-run.md)); very large single files and recovery from a crashed worker have not been exercised.
- Scanned forms with small print come out fragmentary, and VietOCR can turn English form labels into invented Vietnamese. The language and spelling checks flag such pages for review ([E8](../experiments/E8-ak3-appendices-corpus-run.md)); for English-only corpora, compare `rapidocr`.
- A scanned contents page is reported as `missing`: OCR reads it, then the contents filter removes the text ([E8](../experiments/E8-ak3-appendices-corpus-run.md)).
- Legacy-encoded PDFs are re-read by OCR rather than decoded from their font encoding.
